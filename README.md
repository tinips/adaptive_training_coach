# Adaptive Endurance Coach

Adaptive Endurance Coach is a Telegram-based endurance coaching bot with a
FastAPI backend and a PostgreSQL database. An athlete onboards through a
deterministic Telegram conversation (goal, profile, availability, equipment,
health limitations, self-reported baseline), then gets weekly training plans
generated by an LLM, informed by imported workout history and reported
evidence. There is no companion mobile app; workout history reaches the coach
through an Apple Health export, a TCX file, or a screenshot of another app's
workout summary.

For what is and is not built right now, the architectural decisions behind
it, and the status of the active engineering plan, see [STATE.md](STATE.md).
For contributor conventions (linting, typing, tests, migrations), see
[AGENTS.md](AGENTS.md).

## How the pieces fit together

Two Python processes share one PostgreSQL database and the same
service/repository layer:

```text
Telegram  ---long polling---  bot process (python-telegram-bot)
                                      |
                                services / repositories
                                      |
FastAPI process (health, Mini Apps) --+-- PostgreSQL
```

- **FastAPI** (`backend/app/api/`) serves `/health` and `/ready`, plus two
  Telegram Mini App form endpoints: `/webapp/baseline` (the self-reported
  fitness baseline form) and `/webapp/workout-history` (the workout-history
  chart). Mini App requests are authenticated by validating Telegram's signed
  init data, not by login.
- **The Telegram bot** (`backend/app/bot/`) runs long polling. Handlers are
  thin; behavior lives in `backend/app/services/`. Telegram copy and keyboard
  labels are centralized in `app/bot/messages.py` and `app/bot/keyboards.py`.
- **PostgreSQL** is the only source of truth. Schema changes are Alembic
  migrations under `backend/alembic/versions/`, applied by a one-shot
  `migrate` container before `api`/`bot` start.
- The only remaining LLM call that matters end-to-end is the weekly planner.
  A couple of onboarding steps (availability extraction, workout-screenshot
  reading) also call an LLM, but goal selection itself is a deterministic
  menu, not free-text extraction. See STATE.md for why.

## Local setup on Windows

Requirements:

- Windows 10/11 with PowerShell
- Python 3.12+
- Docker Desktop with Linux containers
- A Telegram bot token for live Telegram use
- Optionally, an OpenAI-compatible model key for `LLM_MODE=live`

Install backend dependencies (for running tests/lint outside Docker):

```powershell
cd backend
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -e ".[dev]"

cd ..
Copy-Item .env.example .env
```

Do not overwrite an existing ignored `.env` that already has local
credentials. Never commit `.env`.

## Run with Docker Compose

Set at least `TELEGRAM_BOT_TOKEN` and `TELEGRAM_BOT_USERNAME` in `.env`. For a
private bot, also set `TELEGRAM_ALLOWED_USER_IDS` to a comma-separated list
of Telegram numeric user IDs; the bot ignores every other Telegram user
before their updates reach application services. An empty value disables
Telegram access until an ID is configured.

```powershell
docker compose up --build
```

Compose starts PostgreSQL, runs `alembic upgrade head` via the one-shot
`migrate` service, then starts FastAPI and the Telegram bot. The API is
available at `http://localhost:8000`; the local PostgreSQL port is `55432`.
`adminer` (a Postgres web UI) is also started, bound to `127.0.0.1:8080`.

Useful checks:

```powershell
Invoke-RestMethod http://localhost:8000/health
Invoke-RestMethod http://localhost:8000/ready
docker compose ps
docker compose logs migrate
```

`docker compose down` preserves the database volume. `docker compose down -v`
permanently deletes local application data.

To rebuild just one service after a code change (faster than a full
`up --build`):

```powershell
docker compose up -d --build --no-deps bot   # bot-only code change
docker compose up -d --build --no-deps api   # api-only code change
docker compose up -d --force-recreate --no-deps bot  # .env change only, no rebuild needed
```

## LLM configuration

The default `LLM_MODE=mock` requires no provider key and uses a deterministic
fake model, so the full test suite and a local bot run work without any
credentials. For a live OpenAI-compatible provider (the project targets
DeepSeek), set in `.env`:

```text
LLM_MODE=live
LLM_API_KEY=...
LLM_BASE_URL=https://api.deepseek.com
LLM_MODEL=deepseek-v4-flash
```

Structured LLM calls (the weekly planner, availability extraction) request
output via `function_calling` rather than raw JSON mode, so the schema is
actually sent to the model instead of guessed. Safe usage metadata (model
name, token counts, outcome) is written to `llm_usage`; raw prompts, athlete
text, and screenshots are never logged there.

### Optional screenshot-based workout logging

`SCREENSHOT_IMPORT_ENABLED=true` lets an athlete send a photo of a workout
summary from another app; a vision-capable model (`LLM_VISION_MODEL`, same
DeepSeek credentials) reads the visible metrics, and the athlete confirms
before it is saved. Off by default.

## Optional self-hosted Langfuse tracing

Langfuse is off by default. When enabled it receives only model name,
workflow name, latency, token counts, outcome, and stable error codes — never
prompts, athlete text, screenshots, or credentials. To start the separate
self-hosted stack:

```powershell
docker compose -f docker-compose.yml -f docker-compose.langfuse.yml up --build
```

Open `http://localhost:3000`, create a project, put its public/secret keys in
`LANGFUSE_PUBLIC_KEY`/`LANGFUSE_SECRET_KEY` in `.env`, and set
`LANGFUSE_ENABLED=true`. The app containers use `http://langfuse-web:3000`
internally, not `localhost`.

## Validation

Run from `backend`:

```powershell
pytest
ruff check .
ruff format --check .
mypy app
```

Validate PostgreSQL migrations from the repository root:

```powershell
docker compose up -d db
cd backend
alembic upgrade head
alembic current
alembic check
```

Automated tests use a deterministic model double, mocked provider transports,
and synthetic Apple Health/TCX fixtures; tests marked `@pytest.mark.live`
call a real model provider and a real PostgreSQL test database and are not
run by default. Tests do not prove a live Telegram journey.

## Privacy and safety

- Secrets, LLM API keys, and full free-text profile answers are not logged.
- Apple Health ZIP/XML and TCX uploads are deleted from generated temporary
  paths after processing.
- Screenshot images are read once for extraction and are not retained.
- Every personal repository operation is scoped by the athlete's internal
  user ID.
- Goal and availability intake record intent only; the product does not
  assess goal safety or feasibility, and does not provide medical advice.
